# Stage B parallel Chat worker protocol (2026-11-01)

**Source of truth:** immutable `ALLOCATION.json` and `READY_SNAPSHOT.json`, both committed in the shared base. A worker only uses its exclusive `work/stageb-parallel/worker-N/PENDING.json`. It may read the other shared inputs but must not alter them. Every batch lists the EXACT candidate IDs, original Stage A file and source section start/end lines. Do not scan or reconstruct the rest of the corpus.

## Eligibility already determined

The coordinator has independently parsed every one of 284 Stage A reconstruction files and performed a full candidate-ID preflight, excluding prior approvals (1,071 total in authoritative registry), both prior Codex Stage B selections including holds, global/Modules Stage A holds, provisional duplicate candidates, repeated/conflicting preparation records, and non-ready decisions. Initial queue is the remaining **4,634 exact candidate IDs**. Do not process any other candidate ID, even if it appears in the same section, and never pull from another worker's queue. Do not presume that a chapter's source material is wholly eligible. A batch spans consecutive **eligible-bearing complete source sections** within one chapter; gaps between these sections may contain only context or excluded candidates, and can be traversed for contextual understanding without adding to queue.

## Processing

1. Confirm branch name is `work/stageb/chat-N` and current `PENDING.json` belongs to that same worker. Take the **first** `pending` batch, following source-section order. Its `candidates` list gives exact IDs and `stage_a_artifact` file references; load ONLY these records and relevant `MANIFEST.json`, `CONTEXT_LEDGER.jsonl` and `SECTION_CHECKPOINTS.jsonl` as needed. Keep source chapter scope/context continuous; never inherit a previous theorem's local hypotheses.
2. Check each proposed Stage A `standalone_statement_draft` / `statement`, `hypotheses`, `conclusions`, logical form, quantifier and alternative scope against the pinned Stacks source. Stage A readiness is not independent mathematical approval. Preserve the original theorem and original source locator exactly. Source definitions/notation may be consulted as needed but are not automatically assumptions.
3. **Never read proofs or unsafe raw Stacks slices.** Use `scripts/phase2_safe_source.py` on the pinned Stacks revision for further source verification; this hides proofs, remarks, Situations and informal explanatory argument. Do not work around the mask. If critical material is invisible, register a hold, not a guess. Existing proof-exposure incidents in `flat.tex` and `dualizing.tex` remain excluded.
4. Use a reviewer identity distinct from Stage A. An unchanged/correct Stage A formulation may be independently approved in a worker result; document source-first mathematical equivalence rationale. If any substantive correction is necessary, write the corrected proposal but **hold** it for a second independent reviewer rather than self-approve. Hold difficult mathematical/context or ambiguous source candidates promptly.
5. Store one output JSON object per assigned candidate under `work/stageb-parallel/worker-N/results/<chapter>/section-<start_line>.jsonl`, grouped by complete section. Required fields: `candidate_id`, `source_revision`, `source_file`, `source_line`, `section_start_line`, `stage_a_artifact`, `source_first_review:true`, `reviewer`, `proof_reviewed:false`, `decision` equal to `source_equivalence_approved_pending_materialization` or `held_for_correction_or_context`, and detailed `review_note`. For approvals also record `statement`, `hypotheses`, `conclusions`, `logical_form`, `original_source_statement_tex`; for holds include `hold_reason` and any `proposed_correction`. Do not falsely set `phase2_validated` or `phase3_eligible`.
6. Compare per-section result ID set EXACTLY to that section's eligible `candidate_ids` in the batch. Do not skip a target silently or add unallocated IDs. Commit reviewed complete-section result files and queue progress **together**; no partial section counted as complete. If the entire batch is finished, remove it from your own `PENDING.json.pending` in the same commit. If interrupted mid-batch, retain it pending, with completed section files committed, and resume at first missing full section later. Never delete results. Do not edit other workers' files or common source, scripts, README, allocation, historical outputs or authoritative registry.
7. Push exclusively to your own branch and verify remote SHA. Continue automatically with the next batch until reply capacity ends. Report completed eligible IDs, preliminary approvals, holds, completed batches and remaining pending batches, plus verified latest commit.

## Integration / post-run audit

Run integration separately after the four workers finish, with a new branch based on their pinned common ancestor, merging only their disjoint `worker-N/results` and queue files. Reject any worker commit modifying shared master files or another worker directory. Reconstruct the output ID union and compare to the immutable `READY_SNAPSHOT.json.ready` 4,634 IDs; **no missing and no duplicate IDs** allowed before declaring the initial pass complete. Check approved records for correct source identity, logical scope, reviewer separation and exact final-content digests. Then use the existing `scripts/phase2_review_workflow.py` / `scripts/phase2_authoritative.py` materialization path to register only individually valid, independently approved verdicts. A preliminary Chat result is NOT itself an authoritative overlay; do not append it directly.

The final sweep uses the entire `READY_SNAPSHOT.json.deferred` list for previously held, malformed, duplicated, skipped or unprepared candidates. It separately reconciles canonical active IDs not yet represented, and previously Codex-held cases. All 111 chapters are allocated exclusively for ownership even when 49 have no first-pass ready candidates.

**Efficiency:** no whole-repo startup scan on every reply. One batch, relevant Stage A packet and source-safe context at a time. No skip tables or shared claiming state. Exact ready input is in each batch; deleting completed batch from `pending` is the sole mutable queue state.
