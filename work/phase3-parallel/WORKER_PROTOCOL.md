# Parallel Phase 3 proof-screening protocol (November 1, 2026)

## Source of truth and isolation

Repo `Zengez/mathThm`. All four branches derive from the same `work/phase3/parallel-base` commit, itself based on completed Stage B integration commit `fb84ebe0e2de99d12ba031f1252996d5dc8b1af2`. Stacks source is pinned to `a04446e57ec1fbc252a871afcec7752fb2807b14`. Immutable queue file paths, Git blob SHAs, and source-order batches are recorded in each worker's `PENDING.json`. **Do not dynamically discover other candidates from the corpus.** The frozen Stage B positive decisions total 3,866; 768 held records must be ignored.

The reviewer of Phase 2 Stage B (`chatgpt-stage-b-independent-worker-N`) is distinct from the Stage A reconstructor. Do not pretend that mechanical formatting or a hash creates another independent mathematical review. Do not silently change the positive Stage B content; substantive changes go on hold pending fresh independent source-first review. No candidate becomes Phase 3 eligible just because Stage B said `source_equivalence_approved_pending_materialization`.

## Worker loop — start the first pending batch immediately

1. Verify current Git branch `work/phase3/chat-N` and worker number in `worker-N/PENDING.json`. Take the **first pending** batch. For each listed `sections[].file`, verify its recorded Git blob SHA, section line, and chapter. Read only that section's immutable Stage B result JSONL, in original source order. Process exactly rows with `decision="source_equivalence_approved_pending_materialization"`. Do not process held rows. A batch has whole sections from one chapter; never finish only part of a section.
2. For each positive candidate, confirm exact identity and source revision, source file/line, original Stacks statement, Stage A artifact, Stage B reviewer and substantive `review_note`, `source_first_review:true`, `proof_reviewed:false`, and the reviewed `statement`, `hypotheses`, `conclusions`, `logical_form`. Load relevant Pass 1 raw source/proof locators by exact ID only. Validate against the established `scripts.phase2_authoritative` content and source-provenance rules.
3. Record one **materialization proposal or blocking hold** per positive candidate at `work/phase3-parallel/worker-N/phase2_proposals/<chapter>/section-<line>.jsonl`: exact Stage B content, original source identity, Stage A artifact, Stage B path and blob SHA, reviewer, review note, new check outcome, and any concrete blocker. Do not edit `harvest/PHASE2_AUTHORITATIVE_REGISTRY.json` or its overlay files on a worker branch. Proposals are not approvals. In particular, computing a fresh digest cannot substitute for an independent final-content mathematical review.
4. **Official Phase 3 gate:** before recording an *official* proof decision, require `scripts.phase2_authoritative.load_approved()` to return the ID, with exact matching source identity, statement, hypotheses, conclusions, logical form, and approved content SHA. At initialization, the 3,866 do **not** satisfy this gate. Never fake `phase2_validated`, `phase3_eligible`, `pass3_plausible`, or `published`.
5. As an efficiency measure, a worker **may inspect the pinned full proof provisionally** even while central Phase 2 registration is pending. Such evidence goes only to `worker-N/proof_reviews/<chapter>/section-<line>.jsonl`, clearly labeled `proof_screening_provisional_pending_authoritative_phase2`. It must never be loaded by the official Pass 3 consumer until the coordinator subsequently verifies the identical authoritative formulation and reevaluates the decision. If a worker cannot safely access the full original proof, record `proof_screening_deferred`, not an invented reading.
6. Phase 3 is a **brief proof-plausibility/completeness screen**, not mathematical proof verification. Use the actual pinned original Stacks source and exact Pass 1 `proof_start_line` and `proof_end_line` / URLs. Unlike Stage B, reading proofs is intended for this work. A `plausible` provisional result needs a *complete brief inspection* and actual proof completion evidence, not a truncated packet or the mere presence of `\\end{proof}`; `questionable` requires a concrete uncertainty or missing evidence; `rejected` requires an identifiable positive problem. Do not spend excessive effort on difficult proofs: hold/questionable promptly. Record `candidate_id`, `stage_b_reviewed_content` identity/digest (unregistered proposals labeled as such), `outcome`, `scan_completed`, `reason`, `proof_checked_on` (actual date), pinned proof file/lines, URL/locator, `source_revision`, `proof_screening_confidence:"brief_scan_only"`, `mathematical_audit:"not_audited"`, and explicit `phase2_authoritative_registered`. For a candidate on hold, use an explicit `proof_screening_deferred` reason instead of a fabricated `plausible`.
7. For each completed section, compare the exact set of positive candidate IDs from its Stage B input against BOTH phase2 proposal and proof review/defer output: **exactly one row each, no missing, extra, or duplicate IDs**; no held Stage B IDs in either output. Never mark `phase3_eligible` on a provisional review. Save section files for progress even if a batch is unfinished. Remove a batch from only your own `PENDING.json.pending` in the same commit as all section outputs when its *provisional or admitted* processing is complete. Keep partial batches pending and skip already completed full sections upon resume.
8. Write only under your own `work/phase3-parallel/worker-N/` directory. Never edit another worker's files, shared scripts, staging, source, queue allocation, authoritative registry, published catalog, `data/theorems.json`, or GitHub `main`. Push exclusively to your own branch; verify remote SHA. Continue immediately with the next batch without asking the user for assignments. Report exact IDs, proposals, provisional plausible/questionable/rejected/deferred counts, completed full sections, batches and remaining batches, verified pushed commit.

## Coordinator integration

Only after all workers finish, merge their four disjoint worker subdirectories onto `work/phase3/parallel-reconciled`, based on their common pinned base. Reject any non-worker changes. Perform full ID union audit against the 3,866 **positive Stage B IDs** (no held, missing, extra, duplicate), all file blob integrity, original Stacks source and proof provenance, and exact reviewed final content.

A **separate** controlled Phase 2 materialization must use `scripts/phase2_review_workflow.py` / `scripts/phase2_authoritative.py` with independent positive verdict and exact-content digests. Do not automatically register proposals just because proofs looked plausible. Once that gate passes, import only real complete proof reviews under the correct authoritative `phase2_approved_content_sha256`, through `scripts/harvest_pipeline.py` official Pass 3 validation. Revisit any stale or changed proof/statement before importing. Holds and `questionable` remain out of accepted intake. Publishing/merging accepted theorem records is a further separate operation, subject to provenance, duplicate and licensing checks.

**Efficiency:** the exact work is already queued by whole source-result files; do not do corpus-wide selection or regenerate context on each reply, and do not create claim/skip tables beyond the existing per-worker queue and results.
